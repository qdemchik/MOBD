## 1. Постановка задачи

Спроектировать и реализовать структуру базы данных маркетплейса. База должна:
- содержать не менее 10 сущностей;
- включать связь «многие-ко-многим» через ассоциативную таблицу;
- включать иерархическую связь (самоссылку);
- быть приведённой к 3НФ;
- быть реализованной единым воспроизводимым DDL-скриптом в PostgreSQL.

## 2. Анализ предметной области

### 2.1 Выделенные сущности
Users, shops, addresses, categories, products,
product_categories, orders, order_items, reviews, payments

### 2.2 Бизнес-правила

Пользователи и Магазины: Пользователь может не иметь магазина, либо владеть одним или несколькими магазинами (продавцами).

Товары и Магазины: У товара ровно один продавец (магазин). Магазин может иметь множество товаров.

Категории (Иерархия): Категория может не иметь родительской категории (быть корневой) или иметь ровно одну родительскую категорию. Родительская категория может содержать множество дочерних.

Товары и Категории (M:N): Товар может относиться к нескольким категориям. Категория может содержать множество товаров. Связь реализуется через ассоциативную таблицу.

Заказы и Покупатели: Заказ принадлежит ровно одному покупателю. Покупатель может иметь множество заказов.

Заказы и Товары (M:N): Заказ содержит хотя бы одну позицию (товар). Товар может входить в состав множества заказов. Связь реализуется через ассоциативную таблицу order_items.

Отзывы: Отзыв оставляется к конкретному товару конкретным пользователем. Один пользователь может оставить только один отзыв на один товар.

Оплаты: Каждый заказ имеет ровно одну связанную запись об оплате. Оплата не может существовать без заказа.

Адреса: У пользователя может быть несколько адресов доставки. Адрес принадлежит ровно одному пользователю.

Цены и Рейтинги: Цена товара не может быть отрицательной. Рейтинг в отзыве должен быть от 1 до 5.

## 4. Нормализация до 3НФ

### 4.1 Пример таблицы до нормализации (UNF)

Products_UNF (product_id, product_name, price, shop_id, shop_name, shop_address, category_id, category_name)

### 4.2 Выявленные аномалии
- аномалия обновления; Если магазин меняет адрес (shop_address), необходимо обновить этот адрес во всех строках товаров этого магазина. Если забыть обновить хотя бы одну строку, данные станут противоречивыми

- аномалия вставки; Невозможно добавить нового продавца (магазин) в базу данных, пока он не выставит хотя бы один товар (так как product_id является частью первичного ключа и не может быть NULL)

- аномалия удаления; Если магазин удаляет свой единственный товар, удаление строки из таблицы приведет к потере всей информации о самом магазине и его адресе

### 4.3 Результат нормализации
Разделение на shops, categories, products, product_categories

Shops (shop_id, shop_name, shop_address)
Categories (category_id, category_name)
Products (product_id, product_name, price, shop_id, category_id) (связь M:N вынесена в отдельную таблицу Product_Categories)

## 5. Обоснование первичных ключей

Суррогатные ключи (id SERIAL / GENERATED ALWAYS AS IDENTITY): Используются для всех основных сущностей (users, shops, products, orders и т.д.).
Обоснование: Естественные ключи (например, email для пользователя или order_number) могут быть длинными, изменяться со временем или требовать сложной генерации. Суррогатный ключ гарантирует неизменность, уникальность и обеспечивает высокую производительность при построении индексов и JOIN


Естественные составные ключи: Используются для ассоциативных таблиц (product_categories, order_items).
Обоснование: В таблицах, реализующих связь «многие-ко-многим», составной ключ из двух внешних ключей (product_id, category_id) естественным образом предотвращает дублирование связей и не требует создания дополнительного суррогатного id, который не несет бизнес-смысла

## 7. Словарь данных

1. Таблица users (Пользователи)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор пользователя.
email (VARCHAR(255)) — NOT NULL, UNIQUE. Адрес электронной почты для авторизации и уведомлений.
password_hash (VARCHAR(255)) — NOT NULL. Хэш пароля пользователя.
created_at (TIMESTAMPTZ) — NOT NULL, DEFAULT CURRENT_TIMESTAMP. Дата и время регистрации аккаунта.

2. Таблица shops (Магазины / Продавцы)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор магазина.
owner_id (INT) — NOT NULL, Внешний ключ (FK) на users(id). Пользователь-владелец магазина.
name (VARCHAR(255)) — NOT NULL. Название магазина.
description (TEXT) — Описание магазина и его ассортимента.

3. Таблица addresses (Адреса доставки)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор адреса.
user_id (INT) — NOT NULL, Внешний ключ (FK) на users(id). Пользователь, которому принадлежит адрес.
city (VARCHAR(100)) — NOT NULL. Город доставки.
street (VARCHAR(255)) — NOT NULL. Улица, дом и квартира.
zip_code (VARCHAR(20)) — NOT NULL, CHECK (формат 6 цифр). Почтовый индекс.

4. Таблица categories (Категории товаров)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор категории.
parent_category_id (INT) — Внешний ключ (FK) на categories(id). Идентификатор родительской категории (самоссылка для иерархии). Может быть NULL для корневых категорий.
name (VARCHAR(100)) — NOT NULL, UNIQUE. Название категории.

5. Таблица products (Товары)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор товара.
shop_id (INT) — NOT NULL, Внешний ключ (FK) на shops(id). Магазин-продавец товара.
name (VARCHAR(255)) — NOT NULL. Название товара.
description (TEXT) — Подробное описание товара.
price (NUMERIC(10,2)) — NOT NULL, CHECK (price >= 0). Текущая цена товара в денежном формате.

6. Таблица product_categories (Связь товаров и категорий)
product_id (INT) — Первичный ключ (часть составного PK), Внешний ключ (FK) на products(id). Идентификатор товара.
category_id (INT) — Первичный ключ (часть составного PK), Внешний ключ (FK) на categories(id). Идентификатор категории. Реализует связь «многие-ко-многим».

7. Таблица orders (Заказы)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор заказа.
user_id (INT) — NOT NULL, Внешний ключ (FK) на users(id). Покупатель, оформивший заказ.
address_id (INT) — NOT NULL, Внешний ключ (FK) на addresses(id). Адрес доставки заказа.
status (VARCHAR(50)) — NOT NULL, DEFAULT 'new', CHECK (допустимые статусы). Текущий статус заказа (новый, оплачен, доставлен и т.д.).
total_amount (NUMERIC(12,2)) — NOT NULL, DEFAULT 0. Итоговая сумма заказа.
created_at (TIMESTAMPTZ) — NOT NULL, DEFAULT CURRENT_TIMESTAMP. Дата и время создания заказа.

8. Таблица order_items (Позиции заказа)
order_id (INT) — Первичный ключ (часть составного PK), Внешний ключ (FK) на orders(id). Идентификатор заказа.
product_id (INT) — Первичный ключ (часть составного PK), Внешний ключ (FK) на products(id). Идентификатор товара.
quantity (INT) — NOT NULL, CHECK (quantity > 0). Количество единиц товара в заказе.
price_at_purchase (NUMERIC(10,2)) — NOT NULL, CHECK (price_at_purchase >= 0). Цена товара на момент покупки (фиксируется для истории).

9. Таблица reviews (Отзывы)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор отзыва.
user_id (INT) — NOT NULL, Внешний ключ (FK) на users(id). Автор отзыва.
product_id (INT) — NOT NULL, Внешний ключ (FK) на products(id). Товар, к которому оставлен отзыв.
rating (SMALLINT) — NOT NULL, CHECK (от 1 до 5). Оценка товара в баллах.
comment (TEXT) — Текстовый комментарий отзыва.
created_at (TIMESTAMPTZ) — NOT NULL, DEFAULT CURRENT_TIMESTAMP. Дата публикации отзыва.
Ограничение UNIQUE (user_id, product_id) — Запрещает одному пользователю оставлять более одного отзыва на один товар.

10. Таблица payments (Платежи)
id (SERIAL) — Первичный ключ (PK). Суррогатный идентификатор платежа.
order_id (INT) — NOT NULL, UNIQUE, Внешний ключ (FK) на orders(id). Идентификатор оплачиваемого заказа (связь 1 к 1).
status (VARCHAR(50)) — NOT NULL, DEFAULT 'pending', CHECK (допустимые статусы). Статус транзакции (ожидает, успешен, отклонен).
amount (NUMERIC(12,2)) — NOT NULL, CHECK (amount >= 0). Сумма платежа.
paid_at (TIMESTAMPTZ) — Дата и время фактического проведения платежа.

## 9. Принятые проектные решения

Выбор суррогатных ключей (SERIAL) — стабильность, компактность.

Естественные составные ключи в ассоциативных таблицах —
предотвращение дублирования связей.

Осознанная денормализация: orders.total_amount и
order_items.price_at_purchase — для производительности и
исторической фиксации цены.

ON DELETE CASCADE для зависимых сущностей(order_items, payments),

ON DELETE RESTRICT для критичных (orders, products).

## 10. Ответы на контрольные вопросы

1. **Реляционная модель** — модель данных, предложенная Э. Коддом,
   представляющая данные в виде отношений (таблиц). Отношение —
   таблица, кортеж — строка (один объект), атрибут — столбец
   (одно свойство).
2. **Концептуальная модель** — ER-диаграмма без привязки к СУБД;
   **логическая** — атрибуты, ключи, типы связей; **физическая** —
   конкретные таблицы PostgreSQL с типами и ограничениями.
3. **Первичный ключ** — столбец/набор столбцов, однозначно
   идентифицирующий строку. Требования: уникальность, NOT NULL,
   стабильность.
4. **Суррогатный ключ** — искусственный ID (SERIAL/UUID): стабилен,
   компактен, но не нагляден. **Естественный** — из предметной
   области (email, артикул): нагляден, но может меняться.
5. **Внешний ключ** — столбец, ссылающийся на PK другой таблицы;
   обеспечивает ссылочную целостность.
6. **Связь M:N** реализуется через ассоциативную таблицу с двумя FK,
   образующими составной PK.
7. **Иерархия** — самоссылка: parent_id FK на id той же таблицы
   (список смежности).
8. PostgreSQL поддерживает: PRIMARY KEY, FOREIGN KEY, NOT NULL,
   UNIQUE, CHECK, DEFAULT.
9. **Нормализация** — процесс устранения избыточности и аномалий
   (вставки, обновления, удаления). 1НФ — атомарность; 2НФ —
   зависимость от всего составного ключа; 3НФ — нет транзитивных
   зависимостей.
10. **ON DELETE RESTRICT** запрещает удаление родителя при наличии
    дочерних строк; **ON DELETE CASCADE** удаляет дочерние строки
    автоматически.
