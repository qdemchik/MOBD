## 3. Краткое описание компонентов проекта

### 3.1. Схема базы данных (Лабораторная №1)
Спроектирована и реализована в PostgreSQL схема из 10 сущностей: `users`, `shops`, `addresses`, `categories`, `products`, `product_categories`, `orders`, `order_items`, `reviews`, `payments`.
- Приведена к **3НФ** (аномалии устранены, транзитивные зависимости вынесены в отдельные таблицы).
- Содержит связь **M:N** через ассоциативные таблицы (`product_categories`, `order_items`) и **иерархическую самоссылку** (`categories.parent_category_id`).
- Все таблицы имеют корректные ограничения: `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`, правила `ON DELETE / ON UPDATE`.
- Схема оформлена единым идемпотентным DDL-скриптом (`schema.sql`), повторное выполнение которого воссоздаёт базу с нуля.

### 3.2. Наполнение данными (Лабораторная №2)
База наполнена согласованными тестовыми данными с использованием `generate_series` и `random()`:
- `users` — 100 строк
- `shops` — 10 строк
- `products` — 1500 строк (>1000 по ТЗ)
- `orders` — 1200 строк (>1000 по ТЗ)
- `order_items` — ~3000 строк
- `categories` — 6 строк (с иерархией)
- `addresses`, `product_categories` — по 100+ строк

### 3.3. SQL-запросы разной сложности (Лабораторные №3 и №4)
**Лабораторная** — многотабличные запросы и аналитические представления:
- `INNER JOIN` трёх и более таблиц (товар → категория → магазин)
- `LEFT JOIN` для поиска «сирот» (товары без отзывов)
- Агрегатные функции с `GROUP BY` и фильтрация групп через `HAVING`
- Подзапросы трёх видов: скалярный, с `IN`, с `EXISTS`
- `CTE` и рекурсивный `CTE` для обхода дерева категорий
- Два представления (`VIEW`): `shop_revenue_view` и `products_without_reviews_view`

**Лабораторная №4** — оконные функции и аналитика:
- Ранжирующие функции (`ROW_NUMBER`, `RANK`, `DENSE_RANK`)
- Топ-N в группе через `ROW_NUMBER` + CTE
- Нарастающий итог выручки по дням
- Доля выручки продавца в категории через `SUM() OVER (PARTITION BY ...)`
- Функции смещения `LAG` / `LEAD` для расчёта прироста
- Сравнение оконного и `GROUP BY` подходов

### 3.4. Серверная логика и целостность (Лабораторная №5)
- **Транзакции**: продемонстрированы `BEGIN / COMMIT / ROLLBACK`, свойство атомарности.
- **Функции на PL/pgSQL**:
  - `place_order(...)` — атомарное оформление заказа с проверкой остатка и `RAISE EXCEPTION`
  - `get_seller_revenue(...)` — расчёт выручки продавца за период
- **Триггеры**:
  - `trg_price_audit` — аудит изменения цен (запись в `price_audit_log`)
  - `trg_update_rating` — поддержание денормализованного поля `avg_rating` в таблице `products`

### 3.5. Современные возможности и оптимизация (Лабораторная №6)
- Добавлен столбец `attributes JSONB` в таблицу `products` с характеристиками товаров.
- Написаны запросы с операторами `->>`, `@>` для извлечения и фильтрации по JSONB.
- Сняты планы выполнения «тяжёлых» запросов через `EXPLAIN ANALYZE`.
- Добавлены **B-tree индексы** по внешним ключам (`shop_id`, `product_id`, `order_id`) — тип сканирования изменился с `Seq Scan` на `Index Scan`.
- Создан **GIN-индекс** по столбцу `attributes` для поддержки оператора `@>`.
- Продемонстрирована обратная сторона индексов: замедление массовой вставки данных.

## 4. Принятые проектные решения (обобщение)

1. **Суррогатные ключи (`SERIAL`)** для всех основных сущностей — стабильность, компактность, независимость от изменений бизнес-данных.
2. **Естественные составные ключи** в ассоциативных таблицах (`product_categories`, `order_items`) — предотвращение дублирования связей без лишнего `id`.
3. **Осознанная денормализация**: `orders.total_amount` и `order_items.price_at_purchase` — для производительности и исторической фиксации цены; `products.avg_rating` — для быстрого чтения карточки товара, согласованность поддерживается триггером.
4. **Правила `ON DELETE`**: `CASCADE` для зависимых сущностей (`order_items`, `payments`), `RESTRICT` для критичных (`orders`, `products`).
5. **Разделение логики**: в БД — логика целостности (триггеры, атомарные операции), в приложении — прикладная бизнес-логика (валидация форм, скидки, интеграции).
6. **JSONB вместо JSON** для характеристик товаров — поддержка индексирования и быстрый доступ к полям.
7. **Осознанный выбор индексов**: только под конкретные частые запросы, с подтверждением эффекта через `EXPLAIN ANALYZE`.
